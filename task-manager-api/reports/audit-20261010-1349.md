## Findings

### [CRITICAL] Hardcoded Secrets and Credentials   (AP-01)
File: app.py:13-13
Description: `app.config['SECRET_KEY'] = 'super-secret-key-123'` assigns a signing-key literal in the entry point.
Impact: Anyone with the repository can forge anything signed with the key, and rotating it needs a code change and a deploy.
Recommendation: Read the key from the environment in a configuration module; the application never touches `session`, so an unset key can fall back to a per-process random value instead of a literal. Rotate the old value, it stays in git history. See RP-01.
Contract: safe

### [CRITICAL] Insecure Runtime Configuration   (AP-18)
File: app.py:34-34
Description: `app.run(debug=True, host='0.0.0.0', port=5000)`. Observed at the native configuration: `Debug mode: on`, `Debugger is active!` with a PIN printed, listener on all addresses, and 7 requests that raised an unhandled exception were answered with the interactive-debugger HTML page (500, text/html). Escalated from HIGH: an interactive debugger is reachable from outside the host.
Impact: A debugger console is code execution by design for anyone who obtains the PIN, and the error pages disclose source paths and code.
Recommendation: Make debug an opt-in setting read from configuration (default off) and keep the bind address as a setting with the same default value; replace the default error page with the centralized boundary of RP-09. See RP-17.
Contract: safe (debug off and the framework's default error page replaced, same status codes; the bind address keeps its current default, narrowing it would be contract-changing)

### [CRITICAL] God Module / God Class   (AP-03)
File: routes/report_routes.py:1-223
Description: One module and one blueprint hold two unrelated domain concepts: cross-entity reporting (12-155: counting queries, the overdue rule, per-user aggregation, response assembly) and category CRUD (157-223: validation, persistence, serialization). It mixes persistence, business rules, delivery and presentation. It also imports two helpers it never calls (7).
Impact: Nothing in it can be tested without a web server and a database, and every change to categories or reports lands in the same file.
Recommendation: Split along responsibility: repositories, report and category controllers, thin route modules, one per domain concept. See RP-03.
Contract: safe

### [CRITICAL] Missing or Bypassable Authorization (privileged operation)   (AP-04)
File: routes/report_routes.py:12-101
Description: `GET /reports/summary` returns totals across all tasks, users and categories plus a per-user rollup (`user_productivity`, lines 53-68, with each user's name and completion rate) to any anonymous caller. This is the "management aggregate computed across principals — totals … per-customer rollups" signal of `04-architecture-guidelines.md` §6; it applies whether or not an identity model exists.
Impact: Anyone who can reach the port reads the activity of every user.
Recommendation: Guard the operation with an operator credential read from configuration (`OPERATOR_TOKEN`), compared in constant time, closed by default (answers 403 when unset). It invents no users or roles. See RP-04.
Contract: safe (§6, privileged operation: only a caller that is not an operator observes the new 403)

### [CRITICAL] Missing or Bypassable Authorization (business operations)   (AP-04)
File: routes/user_routes.py:92-151
Description: No operation derives the caller from the request. `PUT /users/<id>` sets `role` and `active` from the body (119-125), so any caller can make any account an admin; `DELETE /users/<id>` removes an account and all its tasks by request id (134-151); `POST /login` issues `'fake-jwt-token-' + id` (207-211) which no route ever verifies; task and category writes and deletes (task_routes.py:85-238, report_routes.py:167-223), `GET /users`, `GET /reports/user/<id>` and `GET /tasks/stats` are open to anonymous callers. Classification per §6: the account-deletion signal requires "an application with no identity model", and §6 defines that as "no login, no session, no token"; this application has a login and issues a token, so that signal does not fire; ordinary task/category writes and plain listings are business operations by §6's explicit list; `GET /reports/user/<id>` is one user's own statistics, not a cross-principal aggregate; `GET /tasks/stats` returns task totals without per-principal data and is not covered by the text (ambiguous, treated as business and proposed; see Verification Coverage).
Impact: Horizontal and vertical escalation: any caller reads, edits or deletes any user's data and promotes itself to admin.
Recommendation: Propose an identity model (verified tokens, principals, an ownership and role policy) and enforce it on the operations, not only on the routes. See RP-04.
Contract: contract-changing: every current client is anonymous and would receive 401/403 on operations that succeed today

### [HIGH] Unsafe Handling of Credentials and Sensitive Data (hash in responses)   (AP-08)
File: models/user.py:16-25
Description: `User.to_dict` serializes the whole record, including `'password'` (the stored hash). It is returned by `GET /users/<id>`, `POST /users`, `PUT /users/<id>` and inside `user` of `POST /login`.

Recommendation: Mask the value while keeping the field and its type. See RP-08.

### [HIGH] Unsafe Handling of Credentials and Sensitive Data (weak password hashing)   (AP-08)
File: models/user.py:27-32
Description: `hashlib.md5(pwd.encode()).hexdigest()` hashes passwords with a fast unsalted digest, and `check_password` compares with `==`.
Impact: One database read yields passwords by lookup tables, and the comparison is not constant-time.
Recommendation: A purpose-built password KDF with a per-hash salt, constant-time comparison, and transparent re-hash of legacy digests on login. The KDF in Werkzeug is already installed as a Flask dependency, so it adds no package. See RP-08.
Contract: safe (login keeps accepting the same passwords, legacy digests are upgraded on login)
