### [CRITICAL] Hardcoded Secrets and Credentials   (AP-01)
File: app.py:7-7
Description: `app.config["SECRET_KEY"]` is assigned the string literal `"minha-chave-super-secreta-123"` directly in source. Additionally, database.py:75-79 seeds three real accounts at every boot with plaintext passwords fixed in source (`admin@loja.com` / `admin123`, and two more), which is a credential literal reaching the runtime datastore, not just a test fixture.

### [CRITICAL] Insecure Runtime Configuration   (AP-18)
File: app.py:8-8
Description: `app.config["DEBUG"] = True` and `app.run(..., debug=True)` (app.py:88) enable Flask's interactive Werkzeug debugger on the same process that binds to `0.0.0.0` (app.py:88) — confirmed at runtime: booting the original produced `* Debugger is active! Recommendation: See RP-17. Read `DEBUG` from configuration, default `False`; mask `secret_key` in the `/health` response (keep the field, replace its value); replace the framework's default error page with the centralized handler of RP-09 while keeping status codes.

### [CRITICAL] Missing or Bypassable Authorization   (AP-04)
File: app.py:47-58
Description: `POST /admin/reset-db` (app.py:47-58) wipes every table with no authentication or authorization check of any kind. This is not an isolated oversight: the whole application has no identity model at all — `POST /login` (controllers.py:167-186) verifies credentials but issues no session, token or cookie, so no later request can be tied to a caller, and no route checks anything. `POST /admin/query` (app.py:59-78, filed separately as AP-02 below) shares the same total absence of a check.
Impact: Any anonymous caller — no credentials, no special knowledge — can permanently delete every product, user and order in the system with a single POST. Vertical privilege escalation is not even required because there are no privilege levels to escalate past.
Recommendation: See RP-04. This requires introducing an identity model (authentication, sessions/tokens, and an authorization policy) before any endpoint can be gated — there is no existing session to scope a check to.
Contract: contract-changing — the application has no identity model today, so every current caller is anonymous; requiring authentication would reject all of them. Proposed, not applied (see below).

### [CRITICAL] Injection-Prone Dynamic Query or Command Construction — arbitrary SQL execution endpoint   (AP-02)
File: app.py:59-78
Description: `POST /admin/query` reads `dados["sql"]` from the request body and passes it directly to `cursor.execute(query)` with no parameterization, no allow-list and no authentication (app.py:61,69). This is not merely injection-prone construction — it is a documented, unauthenticated pass-through that executes any SQL statement an anonymous caller supplies, including `DROP TABLE`, arbitrary `UPDATE`/`DELETE`, or `SELECT` of any row in the database. Escalated to maximum urgency per the catalog: the endpoint is unauthenticated and permits writes.
Impact: Complete compromise of the database's confidentiality, integrity and availability by any anonymous network caller. This is the single most dangerous line in the codebase.
Recommendation: See RP-02. There is no legitimate parameterization of "arbitrary attacker-chosen SQL" — the only correct fix is removing this endpoint from the public surface entirely, or gating it behind strong authentication reserved for operators with a fixed, reviewed set of permitted operations.
Contract: contract-changing — removing or gating a currently-reachable route. Proposed, not applied (see below).

### [CRITICAL] God Module / God Class   (AP-03)
File: controllers.py:1-293
Description: This single 293-line module is bound directly as the Flask view functions for every route in the application (see app.py:11-30) and mixes: (a) delivery/request-parsing for five unrelated domain concepts — products (5-126), users/login (128-186), orders (188-262), the sales report (257-262), and a health/diagnostics check (264-292); (b) business-rule validation embedded in the handlers themselves — price/stock non-negativity, name length, and a hardcoded category allow-list (24-54, duplicated with drift at 64-96, filed separately as AP-12); (c) direct persistence — `health_check` (264-292) opens a cursor and issues three raw `SELECT` statements itself, bypassing the model layer entirely. Three or more responsibility categories in one module, holding several unrelated domain concepts, is the defining signal of this entry (see the AP-03/AP-05 precedence rule in the catalog); no separate AP-05 finding is filed on this module.
Impact: No handler in this file can be unit-tested without a live Flask app and a live database. Every change to any one domain (say, orders) risks a merge conflict or an accidental effect on an unrelated one (say, users) because they share one file and one import surface. This is the pattern that makes every other finding in this report harder to fix in isolation.
Recommendation: See RP-03. Split by domain concept into `controllers/` (one module per use-case group: products, users, orders, reports) with each handler reduced to parse → call → render; move validation into boundary schemas (RP-11) and the domain (RP-05); move `health_check`'s direct queries into a repository method.
Contract: safe — internal module boundaries are not observable; every route keeps its path, method, status codes and body shape.

### [CRITICAL] Unsafe Handling of Credentials and Sensitive Data — plaintext passwords   (AP-08)
File: models.py:105-120
Description: `login_usuario` (105-120) compares the submitted password against `usuarios.senha` with a plain SQL equality and returns it unmodified if found; `criar_usuario` (122-131) inserts the password exactly as submitted, with no hashing whatsoever — not even a fast digest, just the raw string. `get_todos_usuarios` (72-87) and `get_usuario_por_id` (89-103) then serialize the full row, `senha` field included, and `listar_usuarios`/`buscar_usuario` (controllers.py:128-144) return that dict verbatim as the JSON response body — so `GET /usuarios` returns every user's plaintext password to any anonymous caller. database.py:75-79 seeds three accounts this way at every boot. Escalated to CRITICAL per the catalog's explicit rule: "passwords ... are stored recoverably" — plaintext is the maximal case of that condition.
Impact: A single unauthenticated `GET /usuarios` call, or a single database read, discloses every account's real password in cleartext. Because people reuse passwords, this compromises accounts on other systems too, not just this one.
Recommendation: See RP-08. Hash with a purpose-built password KDF (e.g., bcrypt/argon2/scrypt) with a transparent upgrade-on-login path so existing accounts migrate without a forced reset; mask the `senha` field's value in any API response that currently includes it (keep the field and its type) as an immediate mitigation.
Contract: mixed — switching to hashed storage and masking the exposed field's value are safe (values are not part of the shape contract); removing the `senha` field from the response body entirely would be a shape change and is proposed as a further hardening step, not applied.

### [CRITICAL] Injection-Prone Dynamic Query or Command Construction — data-access layer   (AP-02)
File: models.py:289-297
Description: `buscar_produtos` builds its `WHERE` clause by directly concatenating `termo` (LIKE pattern), `categoria`, `preco_min` and `preco_max` — all attacker-controlled — into the SQL string (289-297); this is the clearest single site, but the same construction habit is systemic across the data-access layer: `get_produto_por_id` (28), `criar_produto` (47-50), `atualizar_produto` (57-61), `deletar_produto` (68), `get_usuario_por_id` (92), `login_usuario` (109-111 — an injectable authentication check), `criar_usuario` (126-129), `criar_pedido` (140, 155, 157-161, 164-165), `get_pedidos_usuario` (174, 188, 192), `get_todos_pedidos` (206, 220, 224), and `atualizar_status_pedido` (279-281) all build SQL by string concatenation or f-string-equivalent `+` construction instead of parameter binding. Escalated to CRITICAL (already the default) and flagged at the same urgency as app.py:59-78: several of these sites are reachable with no authentication (`criar_produto`, `criar_pedido`, `buscar_produtos`), and one is on the authentication path itself (`login_usuario`), which is the specific aggravating condition the catalog calls out. Confirmed exploitable at runtime — see the security entries in the replay section: an injected `'` in the search term and an injected boolean-true clause in `login` and in an order's `produto_id` both altered behavior in the baseline capture.
Impact: Data disclosure, corruption or destruction, and authentication bypass, are all reachable through ordinary API calls with no credentials. This is the single highest-leverage class of defect in the codebase and touches nearly every write path.
Recommendation: See RP-02. Replace every string-built statement with parameter binding (`?` placeholders passed to `cursor.execute` as a separate sequence, never pre-substituted). Where a value is used as an identifier rather than data (none found here), use an allow-list instead.
Contract: safe — parameterized queries return the identical result for every legitimate (non-hostile) input; only the response to hostile input changes, which is a security entry, not a contract entry.

### [HIGH] Swallowed or Uncentralized Error Handling   (AP-09)
File: controllers.py:5-12
Description: Every one of the 16 handler functions in this file repeats the identical shape: `try: ... except Exception as e: return jsonify({"erro": str(e)}), 500` (representative instance at 5-12; the same block recurs at 14-22, 60-62, 94-96, 108-109, 125-126, 133-134, 143-144, 163-165, 185-186, 218-220, 226-227, 234-235, 254-255, 261-262, 291-292). Each catches the base `Exception` type — every failure, expected or not, is absorbed the same way — and returns the raw Python exception text (`str(e)`) straight into the response body, which can include driver error text, file paths, or SQL fragments. There is also no top-level/centralized error handler registered anywhere in app.py, so any exception that escapes a handler (there are none observed, because every handler already wraps everything) would otherwise hit Flask's own default page.
Impact: Callers cannot distinguish a validation problem from a database outage from a programming bug — everything is a `500` with an ad-hoc message. Internal implementation detail (exception text) leaks to any caller, every time something goes wrong, in production as much as in development.
Recommendation: See RP-09. Introduce a small domain error taxonomy (not-found, invalid-input, conflict, dependency-failure) and one centralized mapping from that taxonomy to HTTP responses, registered once; handlers stop catching for the purpose of shaping responses and let errors reach the boundary.
Contract: safe — the current status codes (400/401/404/500 as already used per handler) are preserved; only the error message text changes from raw exception text to a safe, fixed message, which the shape comparison does not check (it is the same field, same string type).

Description: `criar_produto` (24-62) and `atualizar_produto` (64-96) repeat an almost line-for-line validation block: required-field presence for `nome`/`preco`/`estoque`, non-negative checks on `preco` and `estoque`. ### [HIGH] Missing Boundary Validation   (AP-11)
File: controllers.py:188-220
Description: `criar_pedido` (188-220) accepts `itens[].produto_id` and `itens[].quantidade` with no type or range check before they reach `models.criar_pedido`, where `produto_id` is concatenated directly into SQL (see AP-02 above) and `quantidade` is used unchecked in `estoque - quantidade` (models.py:164): a negative `quantidade` *increases* stock and can drive the computed `total` negative. `atualizar_status_pedido` (controllers.py:237-255 / models.py:275-283) issues a blind `UPDATE ... WHERE id = <pedido_id>` with no prior existence check, so `PUT /pedidos/999999/status` returns `200 {"sucesso": true}` even though no row exists or changed. `buscar_produtos` (controllers.py:111-126) parses `preco_min`/`preco_max` with `float(...)` inside the same broad `try/except Exception`, so a non-numeric value produces a generic `500` instead of a clear `400`. Escalated to HIGH: the unvalidated `quantidade` reaches the datastore and permits persistently corrupt domain state (stock and order totals can be driven to invalid values).
Impact: A malformed request becomes an opaque server error instead of a clear client error, and — worse — a crafted request can corrupt stock counts and order totals in ways that persist and are discovered far from where they entered.
Recommendation: See RP-11. Validate `produto_id` as a positive integer and `quantidade` as a positive integer at the boundary before calling the model; have `atualizar_status_pedido` check existence first and return `404` when the id does not match a row; wrap the `preco_min`/`preco_max` parse in its own boundary check returning `400` on failure.
Contract: safe — every rejection introduced here targets a value no legitimate client would send (a negative quantity, a non-existent order id, non-numeric price bounds); this passes the legitimate-use test.

### [HIGH] Hard-Wired Dependencies / No Composition Root   (AP-06)
File: database.py:4-11
Description: `get_db()` constructs the `sqlite3` connection itself — including running DDL and seeding data — the first time any caller invokes it, and every layer calls it directly: app.py imports and calls `get_db` at 4, 49, 66, 82; controllers.py imports it at 3 and calls it in `health_check` at 266; models.py imports it at line 1 and every single data-access function calls it. There is no single place where the object graph is assembled — the concrete `sqlite3` driver is referenced from the model layer, the controller layer and the entry point alike, and the database path (`"loja.db"`, database.py:5) is a literal read at the point of use rather than resolved once in configuration.
Impact: No part of the persistence layer can be tested with a substitute connection; every module that touches data is coupled to the concrete SQLite driver and to a hardcoded file path. Swapping the storage engine, or testing with an in-memory database, requires editing every call site.
Recommendation: See RP-06. Introduce a composition root (the entry point) that reads configuration once, creates the connection, and injects it into repository objects that the controllers receive already constructed. No module should call `get_db()` for itself.
Contract: safe — wiring is not observable to a client.

### [HIGH] Mutable Global State   (AP-07)
File: database.py:4-11
Description: `db_connection` (line 4) is a module-level variable, lazily assigned by `get_db()` and read by every request from every layer of the application (`check_same_thread=False`, line 10, is set specifically to paper over the fact that one connection object is shared across Flask's threaded request handling). It is never closed, never pooled, and never bounded — the same single connection object serves the process for its entire lifetime.
Impact: Behaviour under concurrent requests depends on SQLite's own internal locking rather than on anything the application controls; a connection-level error (a lock timeout, a corrupted transaction state) affects every subsequent request until the process restarts, and there is no way to substitute a different connection for a test.
Recommendation: See RP-07. Move the connection out of module scope; construct it once in the composition root and inject it into the layer that needs it (or use a bounded connection-per-request/pool pattern), with lifecycle owned by the composition root, not by a lazily-initialized global.
Contract: safe — provided per-call observable behaviour is unchanged, which it is (single-writer SQLite semantics are preserved either way for this workload).

### [HIGH] Missing Schema-Level Integrity Constraints   (AP-20)
File: database.py:14-53
Description: `usuarios.email` (27-35) is the column `login_usuario` looks up by and expects to identify one account (models.py:105-120), yet the schema declares no `UNIQUE` constraint — `criar_usuario` (models.py:122-131) also performs no pre-check, so two accounts can register the same email today, after which login deterministically resolves to whichever row SQLite returns first, silently locking the other out. `pedidos.usuario_id` (39) and `itens_pedido.pedido_id`/`produto_id` (49-50) are joined on `usuarios.id`/`pedidos.id`/`produtos.id` throughout models.py but declared with no `FOREIGN KEY`, and `criar_pedido` (models.py:133-169) never checks that `usuario_id` refers to a real user — `POST /pedidos` with a fabricated `usuario_id` succeeds today. `produtos.preco`, `pedidos.total` and `itens_pedido.preco_unitario` (19, 41, 51) are all `REAL` — binary floating point used for money — so summed totals can drift by fractions of a cent. Escalated to HIGH: the missing `usuarios.email` uniqueness lets identity be corrupted (two accounts answering to one sign-in email, as described above).
Impact: Every one of these rules is currently enforced nowhere but in application code that has gaps, so the database will eventually record the violation permanently — a duplicate-email account that can never log back in, an order pointing at a user or product that does not exist, or a report total that does not reconcile to the penny.
Recommendation: See RP-19. Add a `UNIQUE` index on `usuarios.email` (verified zero duplicate rows in the seeded data — safe to add) and a `FOREIGN KEY` from `pedidos.usuario_id` to `usuarios.id` and from `itens_pedido.pedido_id`/`produto_id` to `pedidos.id`/`produtos.id` (no existing delete path conflicts with these two). Convert money columns to integer minor units internally, keeping the same decimal-number JSON shape at the boundary.
Contract: mixed — the `UNIQUE` email index, the `usuarios`/`pedidos`/`itens_pedido` foreign keys, and the internal money representation change are all safe (verified zero violating rows; boundary format unchanged; no legitimate client relies on being able to reference a nonexistent user). A `FOREIGN KEY` from `itens_pedido.produto_id` to `produtos.id` is not applied: `DELETE /produtos/<id>` has no existing check for referencing orders, so adding this constraint without first deciding cascade/restrict behavior would change what that endpoint does today; proposed, not applied.

### [MEDIUM] Unbounded Resources and Leaked Handles   (AP-13)
File: models.py:4-22
Description: `get_todos_produtos` (4-22) issues `SELECT * FROM produtos` with no limit, no pagination and no streaming — the same pattern repeats in `get_todos_usuarios` (72-87) and `get_todos_pedidos` (203-233), each backing an API route (`GET /produtos`, `GET /usuarios`, `GET /pedidos`) with no query parameter to bound the result. On today's seed data this returns ten rows; nothing in the code bounds it as the tables grow.
Impact: Response size and latency grow linearly with table size with no ceiling, and — for `GET /pedidos`, which additionally does two nested queries per row (see AP-10) — this compounds badly under load.
Recommendation: See RP-13. Add a default page size with an optional `limit`/`offset` (or cursor) parameter to each of these three endpoints.
Contract: contract-changing if a default limit would silently truncate a response a client currently receives in full; adding pagination as an *opt-in* (existing behaviour by default, limit only applied when requested) would be safe. Proposed as a decision for the team on which default to use — not applied in this pass to avoid guessing the right default.

### [MEDIUM] N+1 and Query-Inside-Loop Access   (AP-10)
File: models.py:171-233
Description: `get_pedidos_usuario` (171-201) and `get_todos_pedidos` (203-233) both, for every order row, open a second cursor to fetch its `itens_pedido` and then, for every item, open a third cursor to fetch the product's name — two additional queries per item, inside a loop, inside a loop.
Impact: Listing orders costs `1 + 2N` round trips instead of a small constant number; this is the kind of defect that passes every test on the ten-row seed dataset and degrades as soon as real order volume exists.
Recommendation: See RP-10. Replace with two set-based queries (or one join): all matching `itens_pedido` for the retrieved `pedido` ids in one query, joined or grouped against `produtos` for names, assembled in memory.
Contract: safe — same result set, fewer round trips; explicit `ORDER BY` preserves the current implicit ordering.
